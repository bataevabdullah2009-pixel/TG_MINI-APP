# Order Flow Specification

## 1. Создание

Клиент создаёт заказ только в контексте одного активного бизнеса. Сервер не доверяет цене, названию, business ownership или availability из клиента.

Обязательные проверки:

- валидный Telegram initData и совпадающий Telegram user;
- бизнес доступен;
- клиент не заблокирован и телефон подтверждён;
- доставка/самовывоз разрешены;
- зона доставки активна;
- позиции доступны и stock достаточен;
- минимальная сумма соблюдена;
- чек присутствует для `TRANSFER`.

## 2. Snapshot и суммы

- `OrderItem.name`, `price`, `quantity` сохраняются из БД.
- `itemsSubtotal` равен сумме snapshot-позиций.
- `deliveryFee` сохраняется snapshot.
- `totalPrice = itemsSubtotal + deliveryFee`.
- Будущие изменения товаров и зон не меняют заказ.

## 3. Основной workflow

`NEW -> ACCEPTED -> PREPARING -> READY -> DELIVERING -> COMPLETED`

Допустимые специализированные состояния:

- `READY_FOR_PICKUP` для самовывоза;
- `READY_FOR_DELIVERY`, `COURIER_ASSIGNED`, `PICKED_UP`, `DELIVERED` для доставки;
- `CANCELLED` и `EXPIRED` как терминальные состояния.

Переходы должны проверяться сервером. Повтор одного и того же перехода не создаёт дубль уведомления/назначения.

## 4. Отмена

- Отмена хранит причину.
- При первой отмене невыполненного заказа количественный stock возвращается.
- Оплаченный заказ требует отдельного решения по возврату.
- Удалять отменённый заказ запрещено.

## 5. Изменение созданного заказа

- Silent price change запрещён.
- Клиент должен видеть новый состав/сумму до продолжения.
- Для MVP безопасный путь: отменить исходный заказ и создать новый.

## 6. Ошибки

Пользователь получает понятные коды и сообщения. Raw Prisma (`P2022` и другие) наружу не возвращается.

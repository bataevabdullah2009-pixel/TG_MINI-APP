# Vitrina AI Specifications

Эта папка является каноническим источником требований к продукту Vitrina AI.
Она предназначена для владельца продукта, разработчиков, тестировщиков, дизайнеров
и AI-агентов, которые впервые открывают репозиторий.

## Как читать спеки

1. Начните с [глобального продуктового спека](00-global/GLOBAL_PRODUCT_SPEC.md).
2. Проверьте [фактический статус функций](00-global/PRODUCT_SCOPE_AND_STATUS.md).
3. Найдите роль пользователя в `01-roles`.
4. Найдите предметную область в `02-domains`.
5. Найдите пользовательский процесс в `03-flows`.
6. Для AI, UX, реализации и проверок используйте соответствующие разделы ниже.

## Структура

- `00-global` - назначение продукта, аудитория, границы и коммерческая модель.
- `01-roles` - роли, ответственность, права и запреты.
- `02-domains` - marketplace, бизнес, каталог, остатки, шаблоны и отзывы.
- `03-flows` - авторизация, заказ, оплата, доставка, запись, профиль и уведомления.
- `04-ai` - клиентский AI, AI продавца, модерация и ограничения.
- `05-experience` - user stories, UX/UI и критерии приёмки.
- `06-technical` - архитектура, Telegram, БД и технические контракты.
- `07-quality` - правила стабильности, изменения и матрица трассировки.

## Статусы возможностей

Каждая спорная возможность должна иметь один из статусов:

- `IMPLEMENTED` - реализована и подтверждена текущим кодом.
- `PARTIAL` - часть сценария работает, но есть явные ограничения.
- `PLANNED` - продуктово согласована, но ещё не реализована полностью.
- `OUT_OF_SCOPE` - не входит в текущий продуктовый объём.

Документ не должен выдавать `PLANNED` или `PARTIAL` за готовую production-функцию.

## Приоритет источников

При противоречии требований применяется следующий порядок:

1. защищённые production-инварианты из `AGENTS.md`;
2. глобальный продуктовый спек;
3. актуальный статус функций;
4. доменный или процессный спек;
5. ролевой спек;
6. технический спек;
7. roadmap и исторические отчёты.

Текущий код показывает фактическую реализацию, но не отменяет продуктовый
инвариант. Если код и спек расходятся, нельзя молча менять поведение: расхождение
фиксируется, затем принимается отдельное решение о коде или документации.

## Правила изменения

- Сначала обновляется спек, затем план, затем код.
- Нельзя менять маршруты, checkout, seller order visibility или Telegram routing
  как побочный эффект другой задачи.
- Новая возможность должна обновить статус, критерии приёмки и связанные роли.
- Новое поле Prisma требует изменения `prisma/schema.prisma` и безопасного
  `docs/manual-*.sql`.
- Технические детали не добавляются в глобальный продуктовый спек.
- Исторические отчёты не являются источником требований.

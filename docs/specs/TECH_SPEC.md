# Vitrina AI Tech Spec

## Stack

- Next.js 15 App Router.
- React 19 and TypeScript.
- Prisma ORM.
- Supabase Postgres in production.
- Telegram Bot API and Telegram WebApp SDK.
- Vercel deployment target.

## Environment

Required production URL variables:

- `NEXT_PUBLIC_APP_URL`: base deployed domain, for example `https://production-domain.vercel.app`.
- `NEXT_PUBLIC_WEBAPP_URL`: Mini App entry, for example `https://production-domain.vercel.app/app`.
- `TELEGRAM_WEBHOOK_URL`: webhook URL, for example `https://production-domain.vercel.app/api/telegram/webhook`.

In production, Telegram URLs must be HTTPS and must not use ngrok, localhost, or 127.0.0.1.

## Routes

- `/app`: global catalog.
- `/app/[slug]`: business page.
- `/admin`: business admin.
- `/admin/super`: SaaS admin.
- `/api/telegram/webhook`: Telegram webhook.
- `/api/health`: health probe.

## API Endpoints

- `GET /api/marketplace/businesses`
- `GET /api/businesses/[slug]/catalog`
- `POST /api/businesses/[slug]/orders`
- `POST /api/businesses/[slug]/bookings`
- `GET /api/telegram/set-webhook`
- `GET /api/telegram/debug`

## AI Chat Agent Rules

- AI отвечает как помощник текущей платформы Vitrina AI.
- AI не выдумывает товары, услуги, цены, остатки, доставку, способы оплаты, график работы и статусы заказов.
- Источником фактов для ответа является только база данных Vitrina AI.
- AI может читать публичные данные всех активных и не заблокированных бизнесов:
  - название;
  - slug;
  - тип бизнеса;
  - описание;
  - адрес;
  - телефон;
  - график работы;
  - текущий статус `Открыто` или `Закрыто`;
  - товары и услуги;
  - категории;
  - цены;
  - наличие и остатки;
  - активные зоны доставки;
  - доступные способы оплаты.
- AI может читать заказ только в одном из случаев:
  - заказ принадлежит текущему Telegram-пользователю;
  - пользователь является owner, manager или admin бизнеса заказа;
  - пользователь является super admin.
- Для общих вопросов вроде `что есть?`, `какие магазины есть?`, `доставка есть?`, `вы работаете?` применяется контекст:
  1. если выбран конкретный бизнес, ответ строится по этому бизнесу;
  2. если бизнес не выбран, ответ строится по marketplace и предлагает выбрать магазин.
- Если товар запрошен без указания бизнеса, поиск выполняется по всем активным бизнесам.
- Если открыт конкретный бизнес, поиск сначала выполняется внутри него.
- Если товар не найден, AI предлагает похожие товары, категории или открыть каталог.
- AI не сообщает, что товара нет в конкретном бизнесе, если пользователь этот бизнес не выбирал.
- Демо-бизнесы не используются как fallback и не подставляются вместо отсутствующего контекста.
- До формирования ответа определяется intent:
  - `marketplace_list_businesses`;
  - `business_info`;
  - `product_search`;
  - `delivery_info`;
  - `payment_info`;
  - `working_hours`;
  - `order_status`;
  - `booking_info`;
  - `fallback`.
- Разрешённые read-only tools:
  - `listActiveBusinesses(query?)`;
  - `resolveBusinessByName(query)`;
  - `getBusinessBySlug(slug)`;
  - `searchProductsAcrossBusinesses(query)`;
  - `searchProductsInBusiness(businessId, query)`;
  - `getBusinessDeliveryInfo(businessId)`;
  - `getBusinessPaymentInfo(businessId)`;
  - `getBusinessWorkingHours(businessId)`;
  - `buildBusinessOpenButton(businessSlug)`;
  - `buildProductOpenButton(productSlug, businessSlug)`;
  - `getCustomerOrders(telegramUserId)`;
  - `getOrderStatus(orderCode, telegramUserId)`.
- Выбранный бизнес и последний товарный запрос сохраняются для Telegram-пользователя в `TelegramChatContext`.
- В лог AI-чата записываются `telegramUserId`, исходный текст, `detectedIntent`, `businessSlug`, `businessId`, `toolsCalled` и `responseSource`. Секреты, bot token и полные платёжные данные в лог не попадают.

## Product Stock and Availability Rules

- Товар имеет один из режимов:
  - `SIMPLE_AVAILABILITY`: только `В наличии` или `Нет в наличии`;
  - `TRACK_STOCK`: числовой учёт остатка.
- В режиме `SIMPLE_AVAILABILITY` поле `stock` может быть `null`, а кнопка добавления активна только при `isAvailable = true`.
- В режиме `TRACK_STOCK` поле `stock` обязательно:
  - при `stock <= 0` пользователь видит `Нет в наличии`;
  - кнопка добавления заблокирована;
  - checkout не принимает количество больше доступного остатка.
- Продавец может быстро изменить цену, наличие, остаток, категорию и состояние скрытия/архива.
- Физическое удаление товара из рабочего интерфейса запрещено. Используются `isAvailable`, hidden или archive.
- `OrderItem` хранит snapshot названия, цены и количества на момент оформления.
- Изменение товара или цены влияет только на новые заказы.
- При создании заказа остаток `TRACK_STOCK` уменьшается атомарно. При отмене заказа или отклонении оплаты остаток возвращается ровно один раз.

## Seller Product Management Flow

- В каталоге продавца есть поиск по названию товара.
- Доступны фильтры `Активные`, `В наличии`, `Нет в наличии`, `Скрытые`, `Архив`.
- Цена и остаток редактируются из списка без длинной прокрутки.
- Удаление товара является мягким: товар скрывается или архивируется.
- Старые заказы продолжают показывать snapshot товара, даже если исходный товар скрыт или архивирован.
- Все изменения ограничены текущим `businessId`; super admin может работать с явно выбранным бизнесом.

## Delivery Zones Flow

- Продавец или super admin может:
  - создать зону;
  - изменить название;
  - изменить город или район;
  - изменить стоимость;
  - изменить примерное время доставки;
  - включить или выключить зону;
  - удалить неиспользованную или архивировать использованную зону.
- Manager не меняет зоны доставки.
- Checkout показывает и принимает только активные зоны выбранного бизнеса.
- Заказ хранит snapshot названия зоны, города/района, стоимости доставки и адреса клиента.
- Изменение или архивирование зоны не меняет старые заказы.
- MVP использует ручные зоны без обязательной карты: город/район, цена, время и активность.
- Яндекс Карты или Google Maps могут быть добавлены отдельной задачей.

## Checkout Idempotency Rules

- Двойное нажатие не создаёт два заказа.
- При первом подтверждении кнопка немедленно блокируется и показывает `Отправляем заказ…`.
- Повторный submit на клиенте игнорируется до завершения запроса.
- Клиент создаёт `idempotencyKey` один раз при входе в checkout и повторно использует его при сетевых retry.
- Сервер проверяет комбинацию текущего пользователя, бизнеса и `idempotencyKey`.
- Одинаковый ключ для одного пользователя, бизнеса и корзины возвращает уже созданный заказ.
- Гарантия обеспечивается уникальным индексом БД и обработкой конкурентного конфликта, поэтому работает при медленном интернете и параллельных запросах.
- Повторный Telegram action или webhook не создаёт дубликат заказа.
- Клиент при повторном ответе показывает `Заказ уже создан` и открывает существующий заказ.

## Payment and Manual Receipt Review Rules

- В MVP доступны `Наличные` (`CASH`) и `Перевод` (`TRANSFER`).
- YooKassa может иметь подготовленную архитектуру, но не включается без production-ключей.
- При переводе клиент обязан загрузить чек.
- Автоматической проверки чека нет.
- Backend создаёт и показывает заказ сразу после успешного checkout.
- JPG, JPEG, PNG, WebP и PDF загружаются через безопасный upload flow только для ручной проверки.
- Повторное решение продавца не меняет заказ и возвращает сообщение `Оплата уже обработана продавцом`.
- Клиент и продавец видят ожидаемую сумму, ссылку `Открыть чек` и один из статусов:
  - `Ожидает проверки продавцом`;
  - `Оплата подтверждена`;
  - `Оплата отклонена`.

## Order Status Flow

- Пользовательские подписи статусов всегда на русском; значения enum остаются английскими.
- Базовый поток самовывоза:
  - `NEW` -> `ACCEPTED` -> `PREPARING` -> `READY_FOR_PICKUP` -> `COMPLETED`;
  - отмена допускается переходом в `CANCELLED`;
  - просроченный необработанный заказ может перейти в `EXPIRED`.
- Базовый поток доставки:
  - `NEW` -> `ACCEPTED` -> `PREPARING` -> `READY_FOR_DELIVERY` -> `COURIER_ASSIGNED` -> `PICKED_UP` -> `DELIVERED` -> `COMPLETED`;
  - legacy-статусы `READY` и `DELIVERING` читаются и показываются на русском, но новые переходы используют детальные статусы.
- Нельзя перейти из финального статуса `COMPLETED`, `CANCELLED` или `EXPIRED` обратно в активный поток без отдельного admin-инструмента и аудита.
- Payment status и order status независимы: загрузка чека не завершает заказ и не подтверждает оплату.

## Courier Flow

- Курьер видит только доставки своего бизнеса.
- В выдачу входят:
  - доступные активные доставки;
  - назначенные текущему курьеру;
  - ограниченное число последних завершённых доставок.
- Курьер может принять доступную доставку только один раз; конкурентное принятие защищается транзакцией.
- Курьер меняет статусы только в разрешённой последовательности: `Принять` -> `Забрал` -> `Доставил`.
- Продавец может назначить активного курьера своего бизнеса.
- Клиент и продавец получают русские статусы, а уведомления используют только production Mini App URL.
- Просроченное назначение освобождается без удаления истории заказа.

## Business Archive/Block Rules

- Бизнес не удаляется физически из production через рабочий интерфейс.
- `isActive = false` означает архив: бизнес скрыт из marketplace, каталога и AI public tools, но заказы и история сохраняются.
- `subscriptionStatus = BLOCKED` блокирует новые заказы и записи, но owner, manager и super admin сохраняют доступ к истории в рамках своих прав.
- `subscriptionStatus = EXPIRED` блокирует новые коммерческие операции до продления.
- Демо-бизнес определяется только `isDemo`; он не является fallback для marketplace или AI.
- Разблокировка и восстановление выполняются явным действием super admin.

## Performance Requirements

- Главная Mini App открывается без ожидания seller/admin данных.
- Marketplace не загружает все товары и заказы каждого бизнеса.
- Каталог запрашивает только нужные поля и не дублирует один и тот же полный список через разные relations.
- Для независимых запросов используется `Promise.all`.
- Для списков используются pagination, `take`/`limit`, cursor или `skip`, а также Prisma `select`.
- Запрещено без лимита загружать все заказы, товары, клиентов или завершённые доставки.
- Заказы продавца:
  - по умолчанию последние 20;
  - фильтр по статусу применяется на сервере;
  - дальнейшие записи загружаются через `Загрузить ещё`.
- Заказы клиента:
  - по умолчанию последние 20;
  - подробности заказа загружаются при открытии, если не вошли в короткий список.
- Курьер получает активные доставки и ограниченное число последних завершённых.
- Для безопасных мутаций продавца и курьера применяется optimistic UI с откатом при ошибке.
- Частичная загрузка показывает skeleton конкретного блока и не блокирует весь экран.
- Используются индексы:
  - `Order(businessId, createdAt)`;
  - `Order(businessId, status, createdAt)`;
  - `Order(customerId, createdAt)`;
  - `Item(businessId, isAvailable, archivedAt)`;
  - `Item(businessId, categoryId)`;
  - `DeliveryAssignment(courierId, status)`.
- Изображения должны иметь ограниченные размеры, lazy loading и не блокировать интерактивность страницы.

## Promo Code Rules

- Продавец, owner или super admin выбранного бизнеса может создать промокод и задать процент скидки.
- Manager может видеть применённую скидку в заказе, но не создаёт и не удаляет промокоды.
- Код:
  - хранится в верхнем регистре;
  - уникален внутри одного бизнеса;
  - содержит только латинские буквы, цифры, `_` и `-`;
  - имеет длину от 3 до 32 символов.
- Процент скидки является целым числом от 1 до 90.
- Промокод можно включить, выключить или архивировать без физического удаления истории.
- Опционально задаются дата начала, дата окончания и лимит использований.
- Checkout проверяет промокод только на сервере для текущего бизнеса.
- Клиентская цена не считается доверенной: сервер повторно получает цены товаров, проверяет остатки, применяет скидку и рассчитывает итог.
- Скидка применяется к сумме товаров до стоимости доставки. Стоимость доставки промокодом не уменьшается.
- Заказ хранит snapshot:
  - код промокода;
  - процент скидки;
  - сумма скидки;
  - сумма товаров до скидки;
  - итоговая сумма после скидки и доставки.
- Изменение или отключение промокода не меняет старые заказы.
- Один idempotency key увеличивает счётчик использования промокода только один раз.
- Если код не найден, выключен, ещё не начался, истёк или исчерпал лимит, checkout возвращает понятную ошибку на русском и не создаёт заказ.

## Seller Analytics Rules

- Под кнопкой и режимом `Управление бизнесом` продавцу доступен раздел `Аналитика`.
- Аналитика открывается отдельной страницей `/app/seller/analytics` и не меняет существующие Mini App маршруты магазина.
- Доступ имеют owner и super admin выбранного бизнеса. Manager получает доступ только если это явно разрешено отдельной политикой; по умолчанию доступ закрыт.
- Все данные ограничены текущим `businessId`.
- Доступны фильтры периода:
  - сегодня;
  - 7 дней;
  - 30 дней;
  - 90 дней;
  - произвольный диапазон.
- Основные показатели:
  - выручка;
  - количество заказов;
  - средний чек;
  - новые клиенты;
  - повторные клиенты;
  - отменённые заказы;
  - конверсия завершения заказов;
  - количество проданных единиц;
  - сумма скидок по промокодам.
- Для выручки, заказов, среднего чека и клиентов показывается изменение к предыдущему периоду той же длины.
- Страница показывает:
  - динамику выручки и заказов по дням;
  - заказы по статусам с русскими подписями;
  - топ товаров по количеству и выручке;
  - топ клиентов по сумме покупок;
  - использование промокодов.
- В расчёт выручки входят оплаченные, завершённые и доставленные заказы без отклонённой оплаты; отменённые и просроченные не входят.
- Средний чек и топ товаров считаются только по заказам, вошедшим в выручку.
- API использует агрегаты, `groupBy`, ограниченные top-списки и Prisma `select`; полные списки заказов и клиентов не загружаются.
- Если данных нет, UI показывает нормальный русский empty state, а не нули без пояснения или техническую ошибку.

# Booking Flow Specification

## 1. Область

Booking резервирует услугу одного бизнеса на конкретный интервал времени и,
если требуется, у конкретного сотрудника.

## 2. Предусловия

- бизнес активен и доступен;
- booking включён;
- услуга активна, доступна и принадлежит бизнесу;
- сотрудник активен и принадлежит бизнесу;
- телефон клиента подтверждён;
- выбранное время не занято.

## 3. Выбор

Клиент выбирает:

- услугу;
- сотрудника или вариант без конкретного сотрудника;
- дату;
- доступное время;
- контактные данные;
- комментарий.

Длительность берётся из услуги. Если она отсутствует, применяется согласованное
default-правило, которое должно быть единым.

## 4. Проверка слота

- UI показывает предварительный список.
- Сервер повторно проверяет слот при создании.
- Отменённые, истёкшие и no-show записи не блокируют будущий слот по
  завершённым правилам.
- Одновременная запись двух клиентов в один слот должна быть предотвращена.

Текущий генератор слотов имеет статус `PARTIAL`: используется фиксированный
набор времени и существующие записи.

## 5. Создание

- Начальный статус `NEW` или совместимый `PENDING`.
- Сохраняются service, staff, start/end, клиент и комментарий.
- Продавец получает уведомление.
- Клиент видит запись в истории.

## 6. Статусы

Рекомендуемый поток:

`NEW/PENDING -> CONFIRMED -> COMPLETED`.

Терминальные альтернативы:

- `CANCELLED`;
- `EXPIRED`;
- `NO_SHOW`.

Повторный переход не создаёт дубли уведомлений.

## 7. Перенос

`PLANNED/PARTIAL`:

- старый слот освобождается;
- новый слот проверяется;
- клиент подтверждает изменение;
- сохраняется причина и история;
- отправляется уведомление.

До завершения этого flow перенос не должен выполняться скрытой заменой даты без
уведомления.

## 8. Отмена

- Клиентская отмена может ограничиваться политикой бизнеса.
- Продавец может отменить с понятной причиной.
- Оплаченная запись требует отдельного refund decision.
- История сохраняется.

## 9. Неявка

- `NO_SHOW` используется для клиента, который не пришёл.
- Неявка сотрудника не должна молча маркироваться как вина клиента.
- Будущая модель должна различать причины.

## 10. Ошибки

Клиент получает понятную причину: слот занят, услуга недоступна, телефон не
подтверждён, бизнес закрыт. Технические ошибки не показываются сырым текстом.

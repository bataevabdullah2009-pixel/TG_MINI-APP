# Payment Flow Specification

## 1. Статус способов

- `CASH` - `IMPLEMENTED`.
- `TRANSFER` - `IMPLEMENTED` с ручной проверкой.
- `TELEGRAM_STARS` - `PLANNED`.
- `YOOKASSA` - `PLANNED`, пока нет завершённой production-интеграции.
- `MANUAL` - внутреннее совместимое значение, не отдельное клиентское обещание.

## 2. Независимость статусов

Payment status и Order status решают разные задачи:

- заказ может готовиться при ожидающей оплате только по политике бизнеса;
- загрузка чека не означает `PAID`;
- доставка не подтверждает перевод;
- завершение заказа не должно молча менять финансовый статус.

## 3. Наличные

- Клиент выбирает наличные, если способ доступен.
- Начальный статус `PENDING`.
- Факт получения денег отмечает уполномоченный участник по бизнес-процессу.
- Курьер видит информацию, нужна ли оплата, но не получает seller financial
  permissions автоматически.

## 4. Перевод

1. Владелец включает перевод и задаёт реквизиты/инструкции.
2. Клиент видит банк, получателя и разрешённую информацию.
3. Клиент загружает JPG, JPEG, PNG, WebP или PDF.
4. Checkout создаёт заказ с `AWAITING_REVIEW`.
5. Владелец открывает proof и сверяет сумму и факт поступления.
6. Владелец подтверждает или отклоняет.
7. Клиент получает результат.

## 5. Подтверждение

- Выполняется Owner или Super Admin в контексте бизнеса.
- Manager не подтверждает перевод по умолчанию.
- Операция проверяет ownership заказа.
- Первое решение фиксируется.
- Повторное решение не меняет результат.
- `PAID` ставится только после подтверждения человека или доверенного webhook.

## 6. Отклонение

- Сохраняется безопасная причина.
- Клиент получает понятное сообщение.
- Отклонение не удаляет заказ.
- Возврат stock зависит от решения об отмене заказа, а не только payment status.

## 7. Proof

- URL создаётся разрешённым upload flow.
- Bucket и тип файла проверяются.
- Service role key не попадает клиенту.
- Изображение не является доказательством зачисления.
- AI-анализ чека отключён и не используется в API или UI.
- В интерфейсе показываются только чек, статус ручной проверки и решение
  продавца.

## 8. Возврат

`PLANNED/PARTIAL`: автоматический refund отсутствует. Payment получает
`REFUNDED` только после реального возврата, выполненного и подтверждённого
человеком или платёжным провайдером.

## 9. Приватность

- Полные реквизиты не логируются.
- Proof доступен только участникам операции.
- Клиент не получает чужой proof.
- Seller не получает доступ к proof другого бизнеса.

# Order Flow Specification

## 1. Область

Заказ создаётся у одного бизнеса из доступных товаров. Server-side checkout
является источником итоговой цены и права на создание.

## 2. До checkout

Клиент:

- находится в конкретном бизнесе;
- добавляет доступные позиции;
- меняет количество в пределах UI;
- открывает итоговую форму.

Корзина другого бизнеса не должна незаметно объединяться с текущей.

## 3. Обязательные данные

- подтверждённая Telegram identity;
- подтверждённый телефон;
- имя клиента;
- непустой список позиций;
- способ получения;
- адрес и зона для доставки;
- способ оплаты;
- payment proof для обязательного перевода;
- idempotency key.

## 4. Серверные проверки

Сервер не доверяет клиентским:

- названию;
- цене;
- скидке;
- итоговой сумме;
- business ownership;
- availability;
- stock;
- стоимости доставки;
- статусу оплаты.

Сервер проверяет:

- бизнес `ACTIVE`, не архивирован и принимает операции;
- клиент не заблокирован;
- телефон подтверждён и совпадает;
- позиция принадлежит бизнесу;
- позиция доступна и не архивирована;
- tracked stock достаточен;
- способ получения включён;
- зона активна и принадлежит бизнесу;
- минимальная сумма выполнена;
- промокод применим;
- перевод включён и proof допустим.

## 5. Расчёт

1. Одинаковые позиции агрегируются.
2. Цена читается из каталога.
3. `itemsSubtotal` считается до скидки.
4. Промокод уменьшает сумму товаров.
5. Доставка добавляется после скидки.
6. Итог сохраняется snapshot.

`total = itemsSubtotal - discountAmount + deliveryFee`.

## 6. Транзакция

В одной защищённой операции:

- списывается tracked stock;
- увеличивается usage промокода;
- создаётся Order;
- создаются OrderItem snapshot.

При конфликте весь checkout откатывается.

## 7. Idempotency

- Ключ создаётся один раз на попытку checkout.
- Повторный сетевой запрос использует тот же ключ.
- Один клиент, бизнес и ключ не создают два заказа.
- Повтор возвращает существующий результат.
- UI блокирует повторный submit, но серверная защита обязательна.

## 8. Начальные состояния

- Order status: `NEW`.
- Cash payment: `PENDING`.
- Transfer payment: `AWAITING_REVIEW`.
- Delivery status зависит от этапа и не заменяет order status.

## 9. Статусы самовывоза

Рекомендуемый поток:

`NEW -> ACCEPTED -> PREPARING -> READY_FOR_PICKUP -> COMPLETED`.

Legacy `READY` читается совместимо, но новые изменения используют более точный
статус, когда это возможно.

## 10. Статусы доставки

`NEW -> ACCEPTED -> PREPARING -> READY_FOR_DELIVERY -> COURIER_ASSIGNED/PICKED_UP -> DELIVERING -> DELIVERED`.

`COMPLETED` может использоваться как бизнес-завершение после доставки, если это
согласовано. Нельзя перескакивать обязательные courier stages.

## 11. Отмена и истечение

- `CANCELLED` и `EXPIRED` сохраняют заказ.
- Причина фиксируется, когда доступна.
- Stock возвращается один раз.
- Активное courier assignment закрывается безопасно.
- Оплаченный заказ требует отдельного решения о возврате.

## 12. Изменение созданного заказа

Silent change состава или суммы запрещён. Пока полноценное согласование
изменений не реализовано, безопасный MVP-путь - отменить исходный заказ и
оформить новый.

## 13. Уведомления

- Продавец получает новый заказ.
- Клиент получает важные изменения статуса.
- Курьер получает назначение или доступную доставку.
- Ошибка уведомления не должна удалять уже созданный заказ.

## 14. Ошибки

Клиент получает стабильную бизнес-причину: товар закончился, бизнес недоступен,
телефон не подтверждён, зона недоступна, промокод неверен, proof отсутствует.
Техническая ошибка не раскрывает Prisma details.
